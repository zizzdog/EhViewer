# EhViewer 改造计划：静态 CBZ 归档与收藏式下载列表

## 一、 项目定位与开发原则

### 1. 一句话定位

把 EhViewer 改造成**静态归档工具**：下载 → 写入标准元数据 → 打包成扁平 CBZ → 源文件可随时移走，下载列表作为**收藏记录**长期留存。

### 2. 核心使用场景（一切设计围绕此场景）

```text
下载画廊
   │
   ▼
写入 ComicInfo.xml 并打包为 downloadLocation/[gid]-[标题].cbz
   │
   ├─ 打包完成后立即删除画廊临时子目录（只留扁平 CBZ）
   │
   ▼
用户定期把 CBZ 移出手机 / 挪到外部存储        ← 省手机空间
   │
   ▼
下载列表仍完整显示（数据库为事实来源）
点击阅读 → 本地文件不存在 → 自动降级为网络在线加载
```

### 3. 三条开发原则

| 原则 | 说明 |
| :--- | :--- |
| **不改上游代码** | 本项目只做功能添加，不替上游修 bug。改上游逻辑会导致上游将来修复时产生合并冲突 |
| **最小侵入** | 改动收敛在自己新增的代码里，不动 `SpiderQueen`、`ReaderScreen`、数据库 schema |
| **不引入运行时负担** | 不为边缘功能增加启动/扫描开销（例如不为“恢复下载项”在启动时遍历解压 CBZ） |

### 4. 两条红线

| 红线 | 含义 |
| :--- | :--- |
| **不得误删文件** | 源图、已归档的 CBZ 绝不能被错误删除 |
| **不得内存/句柄泄露** | 文件描述符、协程、缓存不得泄漏 |

### 5. 关键术语约定

| 术语 | 含义 |
| :--- | :--- |
| 下载列表 | 等同于**收藏列表**，是唯一事实来源 |
| CBZ | **永久产物**，写入一次即归档，之后与 App 无关 |
| 源文件 | 画廊临时子目录及其中的散图，属于**可丢弃的中间产物** |
| 数据库 | SQLite `DOWNLOADS` 表，决定列表展示，与文件是否存在无关 |

## 二、 需求目标

1. **下载根目录平铺**：漫画打包为 `[gid]-[标题].cbz` 直接存放于下载根目录，不保留画廊同名子目录。
2. **下载临时文件与就地直出**：下载期间单页散装图片直接存放在用户设定的下载目录下（`downloadLocation/[gid]-[Title]`），不占用应用内部私有存储；打包时直接向外层根目录创建并写入 `[gid]-[Title].cbz`，打包完成后彻底清理画廊临时子目录。
3. **缩略图内部缓存管理**：封面统一保存在应用内部缓存目录 `cacheDir/download_thumbs/[gid].[format]`，可被安卓系统设置中的“清除缓存”一键释放，且绝不污染系统相册与外部下载目录。
4. **在线阅读降级**：本地 CBZ 文件被移除后，阅读器检测文件缺失自动降级为网络在线加载（`useEhPageLoader`），下载列表仍可借助缓存或网络正常展示缩略图。
5. **规范化 ComicInfo.xml 写入系统（适配 LANraragi 后端与中文标签翻译）**：
   - 修复 EhViewer 原生缺少 `<Title>`、微标签全塞入 `<Genre>` 导致媒体库分类污染、`<Teams>` 乱挂载等缺陷。
   - `<LanguageISO>` 严格遵循 ISO 639-1 两字母小写规范（如 `zh`、`ja`、`en`），杜绝中文或长语言名污染 LRR 标签库；实际语言标签归入 `<Tags>`。
   - 严格适配 LANraragi 官方 `ComicInfo.pm` 插件的标签提取规则。
   - 支持联动“显示标签翻译”设置：开启时输出翻译后的命名空间与标签名（如 `女性:女仆`、`<Penciller>森仓圆</Penciller>`），关闭时输出原始英文。
   - `<Tags>` 附带原生纯小写 `uploader:xxx` 与 `timestamp:xxx` 标签。
   - 彻底移除无意义的 `<Manga>` 标签。
6. **打包完整性校验（防止源文件被损坏归档替换）**：打包流程所依赖的 JNI `archiveFdBatch()` 不检查 `archive_write_header` / `archive_write_data` 的返回值，因此“CBZ 文件存在”并不等于“CBZ 内容完整”。必须在删除源图**之前**校验归档有效性，校验失败则保留源图并标记为可重试的失败态。
7. **业务决策明确：放弃“恢复下载项”功能**：
   - 软件日常运行、下载列表管理、阅读器翻页、封面展示 100% 依赖本地 SQLite 数据库（`DOWNLOADS` 表）。
   - 为避免为了冷门的“恢复下载项”边缘功能而在每次启动/扫描时进行昂贵且容易引发 I/O 阻塞的 CBZ 遍历解密，明确将“恢复下载项”判定为非支持项，直接忽略该功能，保持主干逻辑轻量纯净。

## 三、 已确认的架构取舍（不再作为缺陷讨论）

以下行为是**刻意设计**，评审时不应再当作 bug 提出：

| 行为 | 取舍说明 |
| :--- | :--- |
| 源文件移走后，条目仍显示“已下载” | 表示“我曾经下载过”，是收藏语义的正确表达；不需要区分“已归档”与“文件在本地” |
| 点击卡片播放键会重新下载 | 接受。触发面仅手动点击，菜单中的“全部开始”已排除 `STATE_FINISH`，不会误触发 |
| `readMetadataFromLocal()` 对扁平 CBZ 失效 | 接受。数据库才是事实来源，且正常下载路径的 `pages` / `simpleTags` 来自图谱 API 与 SpiderInfo，不依赖该修复路径 |
| 缩略图放在 `cacheDir`，可被清缓存清空 | 刻意的，让用户能用系统“清除缓存”主动释放；下架画廊的封面会因此丢失，接受 |
| 恢复下载项功能不维护 | 已明确废弃，见第二章第 7 条 |
| 打包成功后整目录删除 `downloadDir` | 上游只删散图 + `SpiderInfo`，本改造改为整目录删除；因 CBZ 已完整写入根目录，源图属冗余 |
| 不为兼容旧目录布局保留双写 | 旧画廊子目录仅在读取侧做兼容回退，写入侧只走扁平方案 |

## 五、 ComicInfo.xml 映射规范与翻译时序设计

### 1. LANraragi `ComicInfo.pm` 映射矩阵

依据 LANraragi 官方 `ComicInfo.pm` 插件对各节点的处理规则，精准映射如下：

| XML 节点 | 取值来源（未开启翻译） | 取值来源（开启翻译） | LANraragi 解析结果 | 说明 |
| :--- | :--- | :--- | :--- | :--- |
| **`<Title>`** | `title` | `title` | 漫画标题 `$title` | **必须补齐**，否则 LRR 丢失标题并被迫回退文件名 |
| **`<Series>`** | 留空 | 留空 | - | 避免将画廊长标题写入导致 LRR 产生大量冗余 series 标签 |
| **`<AlternateSeries>`** | `titleJpn` | `titleJpn` | 外部阅读器展示 | 遵循标准 |
| **`<Writer>`** | 社团纯名称列表（逗号分隔） | 翻译后的社团名称列表 | **`group: [社团名]`** | LRR 会自动向 `<Writer>` 追加 `group:` 前缀 |
| **`<Penciller>`** | 画师纯名称列表（逗号分隔） | 翻译后的画师名称列表 | **`artist: [画师名]`** | LRR 会自动向 `<Penciller>` 追加 `artist:` 前缀 |
| **`<Characters>`** | 角色纯名称列表（逗号分隔） | 翻译后的角色名称列表 | **`character: [角色名]`** | LRR 会自动向 `<Characters>` 追加 `character:` 前缀 |
| **`<LanguageISO>`** | `simpleLanguage?.lowercase()`（如 `zh`、`en`、`ja`） | `simpleLanguage?.lowercase()`（如 `zh`、`en`、`ja`） | **`language: zh`** | **严格保持 ISO 639-1 两字母小写**，杜绝 LRR 产生非法标签 |
| **`<Web>`** | 画廊详情页 URL | 画廊详情页 URL | **`source: https://e-hentai.org/g/...`** | LRR 会自动向 `<Web>` 追加 `source:` 前缀 |
| **`<Genre>`** | 画廊大分类 `category`（如 `Doujinshi`） | 翻译后大分类（如 `同人志`） | **`Doujinshi`** 或 **`同人志`** | LRR 直接作为分类标签入库，Komga 流派分类保持纯净 |
| **`<Tags>`** | 微标签集：`parody:xxx, female:xxx, language:xxx, uploader:xxx, timestamp:xxx` | 翻译微标签集：`原作:xxx, 女性:女仆, 语言:中文, uploader:xxx, timestamp:xxx` | **直通原样入库** | LRR 会按逗号拆分原样加入 tags，命名空间完整保留！ |
| **`<Teams>`** | **保持留空** | **保持留空** | - | 彻底废除 EhViewer 原版将原作塞进超级英雄战队的错误逻辑 |
| **`<PageCount>`** | `pages` | `pages` | 用于页数记录 | 遵循标准 |
| **`<CommunityRating>`** | `rating` | `rating` | 用于评分展示 | 遵循标准 |

> **命名空间前缀取值**：`<Tags>` 中未翻译时使用 `TagNamespace.value` 全称（`female` / `language` / `parody` / `reclass` 等），开启翻译后命名空间与标签名同时替换为 EhTagTranslation 的中文（`女性:女仆`）。语种标签除外——语种固定归入 `<LanguageISO>`，不在 `<Tags>` 中重复出现。

### 2. 标签翻译处理的严格时序保证

为避免“因提前翻译导致英文命名空间丢失，进而无法正确归集到对应 XML 节点”的致命逻辑漏洞，数据流必须遵循以下两阶段：

```text
               原始画廊标签池 (tagGroups 或 simpleTags)
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │ 【第一步：原始英文命名空间分类归集 (Classification)】 │
        └──────────────────────┬───────────────────────┘
                               │ 基于原始英文 namespace 进行分类：
                               ├─ Artist / Cosplayer ──> rawArtists
                               ├─ Group ───────────────> rawGroups
                               ├─ Character ───────────> rawCharacters
                               ├─ Parody ──────────────> rawParodies
                               └─ Female/Male/Language 等 ─> rawTags
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │ 【第二步：条件化内容与命名空间翻译 (Translation)】    │
        └──────────────────────┬───────────────────────┘
                               │ 检查 Settings.showTagTranslations.value:
                               │
           ┌───────────────────┴───────────────────┐
           ▼                                       ▼
     【开启翻译模式】                         【未开启翻译模式】
   1. 画师名通过 EhTagDatabase 翻译         1. 画师名保留原始英文/罗马音
   2. 社团名通过 EhTagDatabase 翻译         2. 社团名保留原始英文/罗马音
   3. 角色名通过 EhTagDatabase 翻译         3. 角色名保留原始英文/罗马音
   4. 大分类映射为中文（如“同人志”）         4. 大分类保留英文（如“Doujinshi”）
   5. 微标签与命名空间同时中文化：            5. 微标签保留原始英文：
      前缀取中文 (female -> "女性")             前缀取英文 ("female")
      标签取中文 (maid -> "女仆")               标签取英文 ("maid")
      拼接为 "女性:女仆", "原作:舰队Collection"   拼接为 "female:maid", "parody:kantai collection"
   6. 附带小写 uploader 与 timestamp 标签    6. 附带小写 uploader 与 timestamp 标签

   注：<LanguageISO> 在两种模式下均为 simpleLanguage?.lowercase()，不参与翻译
                               │
                               ▼
        ┌──────────────────────────────────────────────┐
        │ 【第三步：注入并序列化为标准 ComicInfo.xml】        │
        └──────────────────────────────────────────────┘
```

## 七、 关键技术点备忘

1. **文件名长度安全性**：`info.downloadDirname()` 内部调用 `FileUtils.sanitizeFilename`，强制截断至 200 字节（UTF-8），加上 `.cbz` 后共约 204 字节，满足 Linux 255 字节限制。
2. **下载期间临时文件落盘**：`imageDir` 锁定为用户指定的 `downloadDir`，所有下载期间的图片切片均在外部存储生成，不占用内部存储；打包直接向外层根目录写入，完成后整目录删除 `downloadDir`。
3. **SAF 权限时序安全**：下载路径切换时，系统会先释放旧 URI 权限，因此任何方法在路径设置完成前不得访问旧 `downloadLocation`。`downloadThumbLocation` 等 getter 中不得出现 `mkdirs()` 之类副作用，否则路径变更时可能触发 `SecurityException`。
4. **标签翻译顺序不可逆**：标签归集必须在未翻译状态下通过英文命名空间精准路由到 `rawArtists`、`rawGroups` 等容器中，绝不能在未分类前全局直接替换字符串，否则会导致 `<Penciller>` 等核心节点丢失数据。
5. **恢复下载项功能定位**：日常使用 100% 走 SQLite 数据库，已明确忽略且不维护从根目录 CBZ 逆向解压扫描重建数据库的特性，防止复杂化主流程。
6. **CBZ 是永久产物，一次写对**：元数据写一次就随 CBZ 归档离开 App，事后修正需批量重开 CBZ 改 XML。因此 `<LanguageISO>` 等字段必须一次写对，不能依赖后续修复。
7. **打包校验是源图安全的唯一屏障**：`archiveFdBatch()` 不报告写入失败，`postArchive()` 只判断“CBZ 文件是否存在”。若不做内容校验，写入中途失败会以损坏 CBZ 替换全部源图且不可恢复。校验必须发生在 `dir.delete()` 之前。

## 八、 边界行为与潜在变动记录

> 本章记录**在当前使用习惯下不会碰到**、但语义上存在且值得留档的行为。
> 记录目的是：将来遇到同类现象时能快速定位成因，避免误判为新 bug。

### 1. `DOWNLOAD_DIRNAME` 表语义

```kotlin
// core/data/.../database/model/DownloadDirname.kt
@Entity(tableName = "DOWNLOAD_DIRNAME")
data class DownloadDirname(
    @PrimaryKey @ColumnInfo(name = "GID")  val gid: Long,
    @ColumnInfo(name = "DIRNAME")          val dirname: String,   // 只是名字，不含路径
)
```

- 表中存的是**相对名字**，不是绝对路径。
- 完整路径在运行时由**当前 `downloadLocation` 设置**拼出：
  `val DownloadInfo.downloadDir get() = dirname?.let { downloadLocation / it }`
- `DOWNLOADS` 表**自身没有 DIRNAME 列**（`DownloadEntity` 只有 GID / STATE / LEGACY / TIME / LABEL）。
  `DownloadInfo.dirname` 完全依赖联表取得：
  ```sql
  SELECT * FROM DOWNLOADS LEFT JOIN DOWNLOAD_DIRNAME USING(GID) ORDER BY TIME DESC
  ```

**因此 `dirname` 为空时，下列能力全部失效：**

| 能力 | 依赖点 |
| :--- | :--- |
| 画廊目录路径 | `DownloadInfo.downloadDir` |
| 扁平 CBZ 定位 | `DownloadInfo.archiveFile` |
| 打包目标文件名 | `SpiderDen.archive()` 的 `targetCbz` |
| 归档成功判定 | `SpiderDen.postArchive()` 的 `flatCbzName` |
| 导出 | `SpiderDen.exportAsCbz()` |
| 断点续传目录判定 | `SpiderDen.initDownloadDirIfExist()` |
| 旧目录封面回退 | `DownloadThumbInterceptor` 的 legacy 分支 |
| 恢复下载项去重 | `DownloadScreen.getRestoreItem()` |

**当前状态**：封面缓存已由 `DownloadThumbInterceptor` 与 `dirname` 解耦（只把 `dirname` 留给 legacy 回退分支）。因此**即使 `dirname` 为空，缩略图仍能由 `GALLERIES.THUMB` 取图并落到 `cacheDir/download_thumbs/`**；但 `archiveFile` 仍会返回 `null`，阅读走联网降级。

### 2. `dirname` 为空的触发条件

| 场景 | 说明 |
| :--- | :--- |
| 只导入数据库备份 | `DOWNLOAD_DIRNAME` 表为空 |
| 更换下载目录后 | 见本章第 3 条 |
| 删除条目时勾选删除文件 | `deleteDownload(deleteFiles = true)` 会调用 `removeDownloadDirname()` 抹掉该行 |
| 旧数据库迁移 | `EhDB` 迁移时 `insertOrIgnore` 整表导入；来源库缺该表则为空 |

**隐蔽副作用**：`SpiderDen.downloadDirname()` 在 `dirname == null` 时用**当前标题**推算并**无条件写库**：

```kotlin
dirname = FileUtils.sanitizeFilename("$gid-$title")
EhDB.putDownloadDirname(gid, dirname)
```

这条自动生成的记录**不校验目录或文件是否真实存在**。只要有任何代码路径调用它（`initDownloadDirIfExist()` / `getGalleryDownloadDir()` / `exportAsCbz()`），`DOWNLOAD_DIRNAME` 就会被静默填上"看起来有效、但可能与实际文件不符"的记录。

### 3. 更换下载目录时会发生什么

流程（`DownloadScreen.kt:103-120`）：

1. 释放**所有**旧目录的持久 URI 权限
2. 申请新目录权限
3. 校验为新目录且可写（`keepNoMediaFileStatus(path)`，副作用是创建/删除 `.nomedia`）
4. 写入 `Settings`：`downloadScheme` / `downloadAuthority` / `downloadPath` / `downloadQuery` / `downloadFragment`

| 问题 | 答案 |
| :--- | :--- |
| 会重写 `DOWNLOAD_DIRNAME` 表吗？ | **不会**，一个字节都不改。`downloadLocation` 的 setter 只写 5 个 Settings 键 |
| 会迁移已有文件吗？ | **不会**。全仓库没有迁移代码；且第 1 步已释放旧目录权限，**技术上也无权访问** |
| 怎么保证路径同步？ | **没有同步机制**。唯一保障是第 3 步的可写性探测。这几个 Settings 也没有挂 observer，换目录不会触发任何后台副作用 |

**换完之后的状态**：`downloadLocation` 变了，但 `DOWNLOAD_DIRNAME` 里仍是相对名字 ⇒ 全部条目指向新目录下的不存在路径 ⇒ `archiveFile` 返回 `null`、阅读降级联网；新下载落到新目录；**旧目录中的文件成为孤儿，App 完全不知道它们存在**。

唯一的路径同步机制是「恢复下载项」（`DownloadScreen.kt:255-298`），但它在 `:257` 有 `if (!file.isDirectory) return null` —— **只认目录不认文件**，对扁平 CBZ 无效。本项目已明确废弃该功能。

### 4. 对 `dirname` 为空的条目点播放键会怎样

会触发一次完整重下，且过程有副作用：

1. `ensureDownload()` 因 `archiveFile == null` 直接进入 `STATE_DOWNLOAD`
2. 下载过程中 `downloadDirname()` **自动生成并写入一条 `DOWNLOAD_DIRNAME` 记录**，名字为 `sanitizeFilename("<gid>-<当前标题>")`
3. 下载完成后 `postArchive()` 再次删除画廊临时目录，只留新的扁平 CBZ
4. 条目状态回到 `STATE_FINISH`

**潜在变动（本项目使用习惯下碰不到，但语义上存在）**：

- 新 CBZ 的文件名（`<gid>-<当前标题>`）与备份里旧 CBZ 的文件名（`<gid>-<旧标题>`）**通常不一致**
- `archiveFile` 只按 `dirname` 派生文件名查找，**旧文件名的 CBZ 不会被找到**
- ⇒ 同一 gid 可能出现两个不同文件名的 CBZ，App 只认其中一个，另一个成为永久孤儿（占空间且无法通过 App 删除）

> 根源是 `dirname` 一旦写入便不再变化，而它是文件名的一部分；标题来源（`showJpnTitle` 设置）与上游不同版本的 `sanitizeFilename` 规则都可能造成新旧不一致。

### 5. 与「已确认架构取舍」（第三章）的区分

| 类型 | 例子 | 是否需要处理 |
| :--- | :--- | :--- |
| 第三章：刻意取舍 | 缩略图放 `cacheDir`、源文件移走后仍显示已下载 | 不需要，是设计 |
| 本章：边界行为 | `dirname` 为空导致 `archiveFile` 失效、换目录无同步、重下产生孤儿文件 | **不需要修复**（当前使用习惯碰不到），但留档以便将来定位 |
